# 扩展系统现状调研 · 插件化演进方案

> **本文回答两个问题**：① SilverMoon 现在的「扩展机制」到底是什么、够不够用；
> ② 如果想让**用户自己开发插件**，业界（同技术栈 / 类似形态的开源项目）怎么做，
> 有哪些现成组件库，本仓库该走哪条路。
>
> 事实部分全部标注本仓库文件:行；外部结论全部给链接。**未验证的推断会显式标注**
> 「待验证」，不当作结论用。

## 一、现状：一套"单租户"扩展宿主

### 1.1 全貌

扩展机制不是编译期 Tauri 插件，而是**应用自建的运行时扩展宿主**——因为 Tauri 官方
插件模型是编译期链接的（见 §3.1）。实现在 `apps/desktop/src-tauri/src/commands/extension.rs`（908 行）。

```
app_data_dir/
├── extensions_state.json          # { "<ext_id>": bool } 启用状态（extension.rs:183-209）
└── extensions/<ext_id>/
    ├── manifest.json              # 元数据 + 引擎入口 + 贡献点
    ├── engine/                    # 扩展私有引擎（miaohui = Python sidecar）
    ├── web/dist/                  # 扩展预构建前端（Vue/任意静态站点）
    └── data/                      # 扩展私有数据（引擎写，宿主不碰）
```

**生命周期**：`lib.rs:300` 在 `.setup` 里调 `extension::setup()` → 扫描 `extensions/` →
读 manifest → 对每个**已启用**扩展异步拉起引擎（`extension.rs:236-305`）→ 注册全局热键。
托盘贡献在 `tray.rs` 之前收集（`extension.rs:725-740`）。

**对外命令面**（`lib.rs:505-510`，共 6 条）：

| 命令 | 作用 |
|---|---|
| `ext_list` | 已安装清单（id/name/version/enabled/has_engine/engine_ready） |
| `ext_install` | 安装：`folder` / `zip` / `url` 三种来源（`extension.rs:449-519`） |
| `ext_uninstall` | 停引擎 + 删目录 |
| `ext_set_enabled` | 持久化开关 + 拉起/停止引擎 |
| `ext_invoke` | **通用路由**：转发到扩展引擎的 localhost HTTP（`extension.rs:573-618`） |
| `ext_open` | 打开文件 / 视频跳秒（宿主代执行） |

**引擎协议**：子进程以 `CREATE_NO_WINDOW` 拉起（`extension.rs:212-222`），stdout 打印
`READY <port>` 握手（`extension.rs:389-415`，20s 超时），之后宿主 `POST 127.0.0.1:<port>/<method>`。
`.py` 结尾走系统 Python 解释器（`resolve_python()`，`extension.rs:372-386`），否则直接执行，
Windows 下自动补 `.exe`。

**前端加载**：单一共享窗口 `label="extension"`（`extension.rs:626-660`），
内部 `ExtensionHost.vue` 用 `<iframe src="asset://…/extensions/<id>/web/dist/index.html?ext=&route=">`
加载扩展 UI，经 `postMessage` 与宿主页通信：

```
iframe → 宿主页  { source: "miaohui-ext",  type: "invoke",        reqId, method, payload }
宿主页 → iframe  { source: "lumiluna-host", type: "invoke-result", reqId, ok, data, error }
```
（`ExtensionHost.vue:44-68`）宿主页收到后走 `capabilities.extInvoke()`
（`capabilities/index.ts:1397-1399`）→ `ext_invoke`。

**权限模型**：扩展窗口单独一份 capability `capabilities/extension.json`（windows:["extension"]），
授予 `core:default` + `opener:*` + `fs:allow-read-file`（scope `**/extensions/**`）等。
设计意图写在 `doc/miaohui-migration-plan.md` §1.4/§1.5：**高权限动作由主机代执行**，
`open`/`reveal` 在 `ext_invoke` 里被宿主拦截（`extension.rs:581-593`），不转发给引擎。

### 1.2 真正生效的贡献点只有两个

`contributes` 在 manifest 里声明了四类（`extension.rs:77-129`），但**只有两类被消费**：

| 贡献点 | 状态 | 证据 |
|---|---|---|
| `contributes.hotkeys` | ✅ 生效 | `register_hotkeys()` `extension.rs:678-722` |
| `contributes.tray` | ✅ 生效 | `tray_menu_items()` / `handle_tray_event()` `extension.rs:725-775` |
| `contributes.windows` | ❌ 解析但不用 | 窗口参数硬编码 760×520 / `always_on_top(true)` / `decorations(false)`（`extension.rs:642-652`） |
| `contributes.settings.schema` | ❌ 解析但不用 | 无任何 UI 渲染、无 per-extension 设置存储 |

manifest 里另有三个字段**全仓库无人读取**：

- `permissions`（`extension.rs:53`）——miaohui 声明的 `["opener:open-path","fs:read:ext","ext:invoke"]` 纯属文档；
- `minHostVersion`（`extension.rs:45`）——从不与宿主版本比对；
- `web.defaultRoute`（`extension.rs:71-75`）——前端硬编码 `route || "search"`（`ExtensionHost.vue:37,81,105`）。

### 1.3 参考实现：miaohui

`apps/desktop/miaohui-extension/` 是第一个也是唯一一个扩展包（Python sidecar + 预构建 web UI，
移植自 MIT 项目）。它同时是**事实上的规范**——因为宿主里写死了它的名字：

- 桥接 `source` 硬编码 `"miaohui-ext"`（`ExtensionHost.vue:53`），回复 `"lumiluna-host"`（:57）；
- 默认路由硬编码 `"search"`；
- 窗口标题硬编码 `"SilverMoon · 扩展"`（`extension.rs:647`）。

**第二个扩展要么复用 miaohui 的魔法字符串，要么改宿主。** 这是"垂直切片"而非"平台"的最直接标志。

### 1.4 成熟度坐标：和本仓库自己的皮肤系统比

同一个仓库里，皮肤系统（`commands/skin.rs` + `src/utils/skinSchema.ts`）已经做到了扩展系统还没做的事：

| 维度 | 皮肤系统 | 扩展系统 |
|---|---|---|
| 格式版本 | `formatVersion` 1/2 双版本共存 | 无 |
| 严格校验 | TS 侧白名单校验器，568 行，错误面向用户 | 仅 `serde_json` 反序列化 |
| ZIP 限额 | 条目 ≤200、总量 ≤50MB、单文件 ≤10MB（`skin.rs:59-61`） | **无任何限额**（`extension.rs:903-908` 裸 `archive.extract`） |
| 安装事务 | stage → 前端校验 → commit（原子换入）/ abort | 解压到 `__staging` → 直接 rename |
| 失败回滚 | 有 abort 路径 | **先删旧目录再 rename**（`extension.rs:497-500`），装坏即丢 |
| 开发者文档 | `doc/archive/皮肤开发指南.md` + 两份方案书 + `example/skins/` | 无 |
| 逃生舱 | `--safe-mode` 用默认主题启动 | 无 |

结论：**扩展系统的"安全/健壮"水位线低于本仓库已有的内部标准**，而不是低于业界。

## 二、现状的具体风险（按严重度）

### R1 🔴 扩展 UI 可读任意文件——`asset:` 同源 + scope `**`

`tauri.conf.json:31-41` 把 asset 协议范围开到 `"allow": ["**"]`（无路径限制）；
而扩展 UI 本身就是**用 asset URL 加载的**（`ExtensionHost.vue:36-37` 调 `toAssetUrl`，
即 `convertFileSrc(path, "asset")`——`src/ipc/invoke.ts:40-46`）。

在 Windows 上 asset URL 形如 `http://asset.localhost/<encoded>`，于是扩展 iframe 的
**同源**就覆盖了全部 asset URL。它可以自行 `fetch()` 任意 `asset:` 地址读取文件，
**完全绕过** `capabilities/extension.json` 里那条 `fs:read` scoped to `**/extensions/**` 的限制。

> 该结论由"同源 + scope 全开"两条事实推出，逻辑上很直接，但仍建议做一次 10 分钟确认测试
> （扩展 UI 里 `fetch(convertFileSrc("C:/Windows/win.ini"))`）。**待验证，但风险足够大，
> 不应等验证通过才处理。**

同类：iframe 无 `sandbox` 属性，且 `allow="clipboard-read; clipboard-write"`
（`ExtensionHost.vue:98-104`）——剪贴板读写是敏感能力，目前无条件给。

### R2 🔴 无 CSP

`tauri.conf.json:30` `"csp": null`。主窗口与扩展窗口都没有内容安全策略，
远程脚本/样式/图片不受限。扩展作者一旦引入一个第三方 CDN 脚本，就等于引入任意代码。

### R3 🟠 "宿主代执行"没有按扩展区分

`ext_invoke` 只对 `open`/`reveal` 做拦截后**代执行**（`extension.rs:581-593`），
但拦截后没有查任何 per-extension 策略——**凡是宿主能做的，每个扩展都能请求**。
配合扩展窗口 capability 里的 `opener:allow-open-path` / `allow-open-url` /
`allow-reveal-item-in-dir`，"最小权限"目前只是分层（特权在宿主而非插件进程），
而不是**按扩展授权**。

### R4 🟠 引擎子进程是全权限进程

引擎以 `std::process::Command` 拉起，继承用户全部权限。设计上是刻意的
（`doc/miaohui-migration-plan.md` 只声称"缩小信任面"，没声称沙箱）。
但 UI 上没有任何地方告诉用户这件事——对比 Obsidian 用 `isDesktopOnly` 显式声明、
Figma 在详情页列出 `networkAccess`。

### R5 🟠 安装链路无完整性与限额

- 无 checksum / 签名校验；`url` 安装直接 `reqwest::blocking::get` 下载即解压（`extension.rs:466-479`）；
- 无 ZIP 条目数/总大小上限 → zip bomb / 磁盘打满；
- 引擎启动失败只 `eprintln!`（`extension.rs:300,559`），UI 仍显示"已启用"
  （`engine_ready` 只反映 spawn 那一刻是否拿到端口）。

### R6 🟡 平台化硬编码（详见 §1.3）

### R7 🟡 作者侧零配套

- 无 `@silvermoon/extension-api` 类型包：`shared/types.ts:1250-1265` 只有 `ExtInfo`/`ExtSource`，
  连 manifest 类型都没有，作者拿不到类型提示；
- 无扩展开发指南（皮肤有），无脚手架，`example/` 下只有皮肤；
- 浏览器预览跑不了扩展：实测 `node scripts/check-mock-coverage.mjs` → 后端 183 条命令
  覆盖 113 条，**`ext_list`/`ext_install`/`ext_uninstall`/`ext_set_enabled`/`ext_invoke`/`ext_open`
  6 条全部无 mock**（脚本只发警告不失败）。

### R8 🟡 无更新 / 无版本演进

安装即覆盖，没有"已装版本 vs 包内版本"的比较、没有升级时权限变化的提示、没有回滚。
（仓库里已有可复用的先例：`PresetMarket.vue:19` 用 GitHub raw 的 `index.json` 做市场索引。）

## 三、业界怎么做（调研结论）

### 3.1 先说技术栈内：Tauri 官方**不提供**动态插件

Tauri 插件是 **Cargo crate**：`tauri::plugin::Builder` → `TauriPlugin`，在 `Builder::plugin()` 注册；
ACL（`permissions/*.toml` + capabilities）**在编译期编入**，`tauri-plugin-` 前缀在编译期拼接。

- [Tauri 插件开发指南](https://v2.tauri.app/develop/plugins/)
- [权限](https://v2.tauri.app/security/permissions/) / [capabilities](https://v2.tauri.app/security/capabilities/) / [runtime authority](https://v2.tauri.app/security/runtime-authority/)
- 动态插件特性请求已被关闭：[tauri#8090](https://github.com/tauri-apps/tauri/issues/8090)；
  官方在热安装讨论里回复"处理应用插件超出 tauri 范围……你可以用 asset 协议按需加载脚本。⚠️ 运行任意脚本是**危险的**"：[tauri#6778](https://github.com/tauri-apps/tauri/issues/6778)

**推论**：本仓库自建扩展宿主是正确且唯一的选择。Tauri 只提供原语（asset 协议、sidecar、
localhost、按窗口 capability）。**不要指望引入某个 Tauri 官方机制来解决这件事。**

运行时加载的几条路（含代价）：

| 方案 | 优点 | 代价 |
|---|---|---|
| 子进程 + localhost HTTP（**本仓库现状**） | 语言无关、崩溃隔离、可热重载 | 无沙箱、要自己管生命周期与 socket ACL |
| sidecar `externalBin` | 官方支持 | **构建期**打包，覆盖不了"用户自己装的插件" |
| Deno/Node sidecar | 作者池最大；Deno 有真 `--allow-*` 权限模型 | 仍是特权进程；Node 无权限模型 |
| WASM（Extism / wasmtime） | **真沙箱**、资源限额、进程内 | 作者要换工具链 |

WASM 细节：**Extism** 内嵌 wasmtime，定位就是"在同一个 OS 进程里安全执行不可信的第三方代码"，
host function 即能力面，manifest 默认拒绝（`allowed_hosts` 空=无、`allowed_paths` 空=无、
`memory.max_pages`、wasm `hash`），Rust host SDK `PluginBuilder::{with_function, with_fuel_limit}`。
([announcement](https://extism.org/blog/announcing-extism/) / [host functions](https://extism.org/docs/concepts/host-functions/) / [manifest](https://extism.org/docs/concepts/manifest/) / [docs.rs](https://docs.rs/extism/latest/extism/))。
wasmtime + WASI P2 组件模型 2024-01 起稳定，但 Component Model 1.0 仍在路上、工具链 churn
明显（[Road to 1.0](https://bytecodealliance.org/articles/the-road-to-component-model-1-0)、[兼容性矩阵](https://bytecodealliance.org/articles/component-model-tooling-compatibility)）。
**libloading 动态库方案应直接排除**：Rust 无稳定 ABI，且零沙箱。

同生态的真实先例（值得直接抄形态的）：

- **[Kunkun](https://github.com/kunkunsh/kunkun)**（Tauri 启动器）：扩展商店，从 NPM tarball/JSR/URL/拖拽安装，
  权限声明在 `package.json` 且**安装时展示给用户**，README 明确写"所有扩展默认在沙箱环境运行"。
- **[Xplorer](https://xplorer.space/docs/extensions/overview)**（Tauri 2 文件管理器，alpha）：扩展市场，
  manifest 权限在 Rust 侧校验、由 `XplorerAPI` 网关拦截未声明调用。
  **但它和扩展共享同一 JS 上下文，是护栏不是硬边界**（[permissions](https://xplorer.space/docs/extensions/permissions)）。
- **[Yaak](https://github.com/mountain-loop/yaak)**：Rust `yaak-plugins` crate + JS 运行时包；
  **[Pot](https://pot-app.com/en/docs/plugin.html)**：用户装 `.potext`。
- 非 Tauri 但证明沙箱路线可行：**Zed** 扩展编译为 `wasm32-wasip2`（[docs](https://zed.dev/docs/extensions/developing-extensions)）。

### 3.2 清单式扩展 API 的六个参照系

| 生态 | manifest | 贡献模型 | 隔离 | 兼容策略 |
|---|---|---|---|---|
| [VS Code](https://code.visualstudio.com/api/references/extension-manifest) | `package.json`，`engines.vscode` **不允许 `*`** | `contributes` 约 40 个**封闭**贡献点 | 独立 Extension Host 进程（理由："防止扩展影响启动性能、拖慢 UI 操作、修改 UI"） | `proposed API` 只对 Insiders 开放、禁止出现在已发布扩展 |
| [Obsidian](https://docs.obsidian.md/Reference/Manifest) | `manifest.json`：`id`/`version`/`minAppVersion`/`isDesktopOnly` | 少量 | **无沙箱**，`isDesktopOnly` 显式承认可用 Node/Electron API | 生命周期 `onload`/`onunload` 必须对称 |
| [Raycast](https://developers.raycast.com/information/manifest) | npm `package.json` 超集 | command（`view`/`no-view`/`menu-bar`）+ `interval` | 进程隔离 | 类型化 preferences schema |
| [Figma](https://developers.figma.com/docs/plugins/manifest/) | `manifest.json` + `api` 版本（不自动升级） | `main`(逻辑) + `ui`(界面) 双入口 | 逻辑沙箱（无 fetch/DOM）+ iframe UI，**消息传递** | `networkAccess.allowedDomains` 默认 `["none"]`，`*` 需写理由，列表公开在社区页 |
| [WebExtensions MV3](https://developer.mozilla.org/en-US/docs/Mozilla/Add-ons/WebExtensions/manifest.json/permissions) | `manifest.json` | — | 站点隔离 | `permissions`（安装时）/ `optional_permissions`（运行时 `permissions.request()`）分离、可撤销 |
| [Grafana](https://grafana.com/developers/plugin-tools/publish-a-plugin/sign-a-plugin) / [Home Assistant](https://developers.home-assistant.io/docs/creating_integration_manifest/) | 目录内 `plugin.json` / `manifest.json` | 启动扫描挂载 | 后端独立的插件进程 | Grafana **默认拒绝未签名插件**，`MANIFEST.txt` 带 sha256 + PGP |

### 3.3 插件 UI 的技术选型（Vue 3 + Vite 场景）

| 方案 | 评价 |
|---|---|
| **iframe + [penpal](https://github.com/Aaronius/penpal)**（或 [comlink](https://github.com/GoogleChromeLabs/comlink)） | 小而稳，zero-dep，最贴合"宿主页 ↔ 插件页"两页模型。**本仓库已经是这个形状**，只是桥接是手写的 |
| [@remote-dom/core](https://github.com/Shopify/remote-dom)（Shopify） | 天花板最高：插件**不碰真实 DOM**，宿主决定存在哪些元素/属性/事件（Shopify/OpenShift/DatoCMS 在用） |
| Web Components / Shadow DOM（Vue `defineCustomElement`、[Lit](https://github.com/lit/lit)） | 只隔离 CSS，**不隔离 JS**；适合"半可信"插件 UI |
| [@module-federation/vite](https://github.com/module-federation/vite) | Vite 官方推荐、有 Vue 示例；但这是**代码共享**不是安全边界，remote 与宿主同 realm |
| [wujie](https://github.com/Tencent/wujie) | iframe(JS) + shadow DOM(CSS)，开箱隔离；有 Vite 边缘 bug |
| ❌ [qiankun](https://github.com/umijs/qiankun) | 最新版 2023-11，[Vite 支持 issue #1257](https://github.com/umijs/qiankun/issues/1257) 2021 年开到现在，Vite 下沙箱"完全失效"（#3125） |
| ❌ single-spa | 无隔离；❌ ShadowRealm：Stage 2.7，无引擎实现 |
| [quickjs-emscripten](https://github.com/justjake/quickjs-emscripten) | 可在 webview 里跑不可信逻辑（无 DOM），~0.5MB WASM |
| [SES/Endo](https://github.com/endojs/endo) | 在**插件自己的 iframe/Compartment** 里可用；**绝不要在宿主 realm 调 `lockdown()`**，会冻住自家 intrinsics |

> ⚠️ **Tauri 专属坑（对本方案很关键）**：把插件 iframe 加上
> `sandbox="allow-scripts"` 会得到 **opaque origin**——WebView2 下 `crypto.subtle` 变成 undefined，
> 且 Tauri IPC **静默挂起**（[tauri#16219](https://github.com/tauri-apps/tauri/issues/16219)，2026-10）；
> iframe 内 IPC 回调另有长期 bug（[#6204](https://github.com/tauri-apps/tauri/issues/6204)）。
> **所以正确的动作是"保持宿主页 + postMessage 桥、把 origin/scope/CSP 修好"，
> 而不是顺手给 iframe 加 `sandbox` 属性** —— 那会把现在的可用实现直接搞坏。

### 3.4 提炼出的十二条最佳实践

1. **一份严格校验的 manifest + 真实版本区间**：`id`/`name`/SemVer `version`/`minHostVersion`（**拒绝 `*`**）。
2. **贡献点是数据不是代码**：封闭、有文档的贡献点词表，才能在**跑插件代码之前**校验与渲染 UI。
3. **设置项用类型化 schema**（text/password/checkbox/dropdown/file/directory + required + default），别用自由 JSON。
4. **第一天就把执行隔离出 UI 进程**，并用声明式激活事件做**懒加载**。
5. **插件是普通 JS 就大声说**：加 `isDesktopOnly` 式能力标志，按平台/信任级别决定是否加载。
6. **网络默认拒绝 + manifest 白名单 + 展示给用户**（Figma 模型）。
7. **特权核心与 UI 用消息传递切开**——早做很便宜，事后无法补。
8. **区分安装时权限与运行时权限，支持撤销**，并提供状态查询 API 让插件优雅降级。
9. **在 manifest 里给插件 API 版本号，且永不自动升级**。
10. **记录来源与完整性**：`requirements` 钉版本 + hash/签名，宿主可拒绝被篡改的包。
11. **先决定更新路径再决定审核路径**：Obsidian 走 GitHub Release（更新不复审），Raycast 走 PR 复审。
12. **生命周期对称 + 崩溃隔离**：`onload`/`onunload` 必须成对释放资源，单个插件出错不带崩宿主。

## 四、对本仓库的建议

### 4.0 先做一个决定：信任模型

这决定后面所有取舍，**必须先拍板并在 UI 上明说**：

- **方案 A（Obsidian 模型，务实）**：扩展是"用户信任的作者"写的，不沙箱；
  宿主只做**能力网关**（per-extension 权限表 + 安装时展示 + 完整性校验）。
  代价：装扩展≈装软件。收益：一周内能落地，作者体验好。
- **方案 B（Figma/Extism 模型，严格）**：扩展逻辑跑在 WASM 沙箱里，UI 在 iframe，
  默认零能力，按 manifest 逐项授权。代价：作者要学 Extism PDK，工具链多一层。
  收益：可以放心做"一键安装社区插件"的市场。

**建议：先 A 后 B**，但**在 Phase 1 就把数据结构按 B 设计**（权限表、签名位、能力清单），
否则后面要动 manifest 格式与已装扩展。

无论选哪个，**当前"权限字段纯装饰"的状态必须结束**——这是最刺眼的一点。

### 4.2 Phase 2：从"能跑一个扩展"到"能承载多个插件"（1–2 周）

1. **发布作者 SDK**：`packages/extension-api/`（仓库已有 `packages/api-spec`、`packages/shared-assets` 先例）。
   内容：`ExtManifest` 类型、`defineExtension()`、`ExtBridge`（`invoke`/`on`/`open`）、
   Vite 插件（产出 `web/dist` + 注入 id）、脚手架模板。**这是"让用户自己开发插件"的最低门槛。**
2. **写 `doc/扩展开发指南.md` + `example/extensions/hello-world/`**，完全照皮肤那套
   （`doc/archive/皮肤开发指南.md` + `example/skins/`）的规格来。
3. **补齐贡献点**：`contributes.commands`（注册到主界面）、`contributes.settings.schema`（真正渲染 settings UI）、
   `activationEvents`（**懒加载**，别像现在这样启动时把所有启用扩展的引擎全拉起来）。
4. **更新机制**：记录安装来源 + 版本，做 `ext_check_update`；升级时 diff 权限并提示。
   市场索引直接复用 `PresetMarket.vue:19` 的 GitHub raw `index.json` 模式。
5. **补 mock**：让 6 条 `ext_*` 命令在浏览器预览里可用（`check-mock-coverage.mjs` 现在有 70 条缺口）。
6. **稳定性**：`manifest.json` 加 `$schema` 指向发布的 JSON Schema，作者编辑器即可校验。

### 4.3 Phase 3：按需升级隔离（取决于 §4.0 的选择）

- 要跑**不可信**插件逻辑 → **Extism**（进程内、host function 即 ACL、fuel/内存限额、
  manifest 默认拒绝），比自建 Deno sidecar 权限层便宜得多。
- 插件 UI 要**进主界面** → `@module-federation/vite`（打包机制，不是安全边界）
  或 **remote-dom**（宿主控 DOM，天花板最高）。
- 打包成**声明式贡献点**（列表项 / 详情页区块 / 设置卡片）能覆盖 80% 需求的话，就别上微前端。

### 4.4 明确不要做的

- ❌ 不要因为"要平台化"而砍掉现有的**引擎进程隔离 + 宿主代执行**——那是本仓库最强的设计。
- ❌ 不要给插件 iframe 直接加 `sandbox="allow-scripts"`（见 §3.3 的 Tauri #16219）。
- ❌ 不要用 libloading 动态库；不要把"插件 JS 跑在主 webview 里"当作安全边界。
- ❌ 不要引入 qiankun（无 Vite 路径）/ single-spa（无隔离）/ EMP / originjs federation（已停更）。
- ❌ 不要在没有 per-extension 授权之前做"一键安装任意社区扩展"的市场。

## 五、一句话总结

现在的扩展机制是一套**设计方向正确、但只服务一个特定扩展**的垂直切片：
"子进程引擎 + 声明式 manifest + 宿主代执行高权限动作 + 按窗口 capability"这四件事都对，
业界（VS Code 的进程外 host、Figma 的特权核心/UI 分离、Grafana 的目录扫描 + 签名）
也确实是这么做的。真正缺的是**把它变成平台的那层**：权限从装饰变成执行、
UI 从共享 asset 源切出去、manifest 字段从"解析了不用"变成"解析即生效"、
再加上作者 SDK + 开发指南 + 示例。这三件事做完，才算"用户能自己开发插件"。
