# SilverMoon 扩展开发指南（扩展 API v2）

本文面向**扩展作者**：读完你应该能写一个装得上、跑得起来、界面能跟宿主对话的扩展包。

- 系统怎么来的、为什么这么设计：见[扩展系统调研与插件化演进方案](./扩展系统调研与插件化演进方案.md)；
- 皮肤文件格式本身（skin.json 怎么写）：见[皮肤开发指南](./archive/皮肤开发指南.md)；
- 可直接跑的参考实现：`example/extensions/hello-world/`（最小扩展）与
  `example/extensions/skin-manager/`（皮肤扩展）。

> **契约冻结于 2026-10-11（扩展 API v2）。** 文中所有字段名、方法名、消息格式都以
> `src-tauri/src/commands/extension.rs` 的 `ExtManifest` 为准；两者冲突时以代码为准，
> 并请提 issue 让文档跟上。

## 一、扩展是什么

扩展不是「编译进主程序的插件」（Tauri 官方插件是编译期链接的 Cargo crate，做不到运行时安装），
而是**应用自建的运行时扩展宿主**加载的一个独立包：

```
app_data_dir/                            ← Windows: %APPDATA%\cn.cool.silvermoon\
├── extensions_state.json                ← { "<扩展 id>": true }  启用状态
└── extensions/<扩展 id>/                ← 一个扩展 = 一个目录
    ├── manifest.json                    ← 必须：元数据 + 入口 + 贡献点
    ├── engine/                          ← 可选：扩展私有引擎（任意语言，跑成子进程）
    ├── web/dist/index.html              ← 可选：扩展自带前端（预构建静态产物）
    ├── themes/<主题名>/skin.json        ← 可选：扩展自带的皮肤
    └── data/                            ← 宿主创建，引擎私有数据目录
```

一个扩展由三块拼成，**三块都可以单独存在**：

| 组成 | 必需 | 是什么 | 谁执行 |
|------|------|--------|--------|
| `manifest.json` | ✅ | 声明式清单：元数据、引擎入口、贡献点、权限 | 宿主解析，不执行 |
| 引擎（`engines`） | ⬜ | 子进程 + 本地 HTTP 服务，扩展的全部逻辑在这里 | 你的程序，宿主只拉起与转发 |
| 前端（`web`） | ⬜ | 预构建静态站点，跑在共享扩展窗口的 iframe 里 | WebView，与宿主页 postMessage 通信 |
| 皮肤（`contributes.themes`） | ⬜ | skin.json + 资源，纯数据 | 宿主校验并应用 |

三个关键设计，决定了你写扩展的方式：

1. **扩展 UI 与扩展逻辑分家。** iframe 里没有 Tauri IPC、没有 `@tauri-apps/api`，
   它只能通过 `postMessage` 请求宿主页，宿主页再转发。这是安全边界，不是麻烦。
2. **高权限动作由宿主代执行。** 「打开文件 / 在文件管理器里定位 / 视频跳秒」这类事情，
   扩展只能**请求**，宿主看权限清单决定做不做。扩展进程永远不直接持有这些能力。
3. **权限默认在，声明即收紧。** 没写 `permissions` 字段的老包按兼容模式放行（迁移期），
   一旦你写了数组，就逐项严格校验 —— 写漏一项就真的会被拒。

## 二、五分钟上手：hello-world 拆解

参考实现：`example/extensions/hello-world/`。

```
hello-world/
├── manifest.json
├── engine/serve.py          ← 最小引擎：本地 HTTP 服务 + READY 握手
└── web/dist/index.html      ← 纯静态，双击也能开（只是打不通宿主）
```

它只有两个文件要写：`web/dist/index.html`（纯静态单文件，不需要任何构建工具）
和 `engine/serve.py`（40 行 Python）。演示的是**完整链路**：
读设置（`settings:get`）、写设置（`settings:set`）、调自己的引擎方法（`greet`）。

```jsonc
{
  "id": "hello-world",
  "name": "Hello World",
  "version": "1.0.0",
  "author": "你自己",
  "license": "MIT",
  "minHostVersion": ">=2.0.0",          // 比较的是扩展 API 版本，不是产品版本 0.1.0
  "web": { "dist": "web/dist", "defaultRoute": "home" },
  "contributes": {
    "windows": [
      { "route": "home", "title": "Hello World", "width": 680, "height": 480,
        "alwaysOnTop": false, "decorations": false }
    ],
    "hotkeys": [
      { "accelerator": "Ctrl+Alt+H", "route": "home", "action": "toggle" }
    ],
    "tray": [
      { "id": "open", "title": "打开 Hello World", "action": "open:home" }
    ],
    "settings": {
      "schema": [
        { "key": "greeting", "type": "text", "label": "问候语", "default": "你好" },
        { "key": "count", "type": "number", "label": "计数器", "default": 0 }
      ]
    }
  },
  "permissions": ["ext:invoke"],
  "activationEvents": ["onHotkey", "onTray", "onInvoke"],  // 不写就是 onStartup（启动即拉引擎）
  "engines": {
    "cmd": "engine/serve.py",                 // 相对扩展根目录；.py 用系统 Python 拉起
    "args": [],
    "supportEnv": "HELLO_WORLD_DATA_DIR",     // 宿主把 <扩展目录>/data 创建好并注入这个名字
    "readyLine": "READY <port>"
  }
}
```

装上去（设置 → 扩展 → 「从文件夹安装」，选 `example/extensions/hello-world`），
打开方式二选一：

- 按 `Ctrl+Alt+H`（全局热键，切窗口）；
- 托盘菜单 → 「打开 Hello World」。

界面里点几下，你会看到设置值被真的读写、调用记录被打印出来。

## 三、目录结构详解

| 路径 | 必需 | 说明 |
|------|------|------|
| `manifest.json` | ✅ | 必须在扩展**根目录**。解析失败该扩展直接跳过（日志里有 `[ext] 跳过 …`） |
| `engines.cmd` 指向的文件 | 声明了 `engines` 就必需 | 相对扩展根目录。Windows 上若不以 `.exe` 结尾会自动补 `.exe` |
| `web.dist` 目录 | 声明了 `web` 就必需 | 相对扩展根目录，里面必须有 `index.html` |
| `data/` | 宿主创建 | 引擎私有数据。宿主只 `mkdir`，不读不写不清理（卸载扩展会整目录删掉） |
| `themes/<目录>/skin.json` | 声明了 `contributes.themes` 就必需 | 皮肤格式见[皮肤开发指南](./archive/皮肤开发指南.md) |

**扩展目录本身的约束**（宿主只服务这些范围）：

- 扩展 UI 走独立的 `ext:` 协议，**只能读到「扩展根目录以内」的文件**（更上层目录、含 `..`
  的路径一律 403）；
- 扩展 id 就是目录名，**卸载 = 删掉 `extensions/<id>/`**，所以不要把用户数据存在扩展目录之外
  还指望能清理干净；反过来，扩展目录里的东西卸载时一定会丢。

## 四、manifest.json 全字段

字段名一律 **camelCase**（Rust 侧 `#[serde(rename_all = "camelCase")]`）。
下面这张表就是全部 —— 没有隐藏字段。

### 4.1 顶层元数据

| 字段 | 类型 | 必需 | 说明 |
|------|------|------|------|
| `id` | string | ✅ | 全局唯一。同时是**目录名**，也是 `ext:` 协议与桥消息里的身份。建议只用小写字母/数字/连字符/点（如 `com.yourname.thing`）。空 id 的包会被直接跳过 |
| `name` | string | ✅ | 显示名，出现在扩展列表与扩展窗口标题栏 |
| `version` | string | ⬜ | 语义化版本。同 id 重新安装即覆盖更新 |
| `author` | string | ⬜ | 作者 |
| `license` | string | ⬜ | 许可协议标识（`MIT` / `Apache-2.0` …） |
| `minHostVersion` | string | ⬜ | **语义化版本区间**，比较对象是**扩展 API 版本** `EXT_API_VERSION`（当前 `2.0.0`），**不是产品版本 `0.1.0`**。缺省 = 不限；显式写 `"*"` 会被**拒绝**（逼作者给真实区间） |
| `permissions` | string[] | ⬜ | 权限清单，见[第五章](#五权限模型)。**省略整个字段** = 兼容模式放行；一旦写了数组就严格校验 |
| `activationEvents` | string[] | ⬜ | 引擎何时被拉起，取值 `"onStartup"` / `"onHotkey"` / `"onTray"` / `"onInvoke"`。**省略 = 等同 `["onStartup"]`**（旧包行为：启用就拉起引擎）。**声明了但不含 `onStartup` = 真正的懒加载**：启动时不动引擎，直到第一次被热键/托盘打开，或第一次调用引擎方法时才拉起 |
| `engines` | object | ⬜ | 扩展引擎，见 4.2。不写就是纯 UI 扩展 / 纯皮肤扩展 |
| `web` | object | ⬜ | 扩展前端，见 4.3 |
| `contributes` | object | ⬜ | 贡献点，见 4.4 |

关于 `minHostVersion` 再啰嗦一句：`">=2.0.0"`、`"^2.0"`、`"~2.0.0"` 都是合法区间写法，
写 `">=3.0.0"` 的包在当前宿主上**装着也是灰的**（`compatible: false`，引擎不会被拉起，
UI 上会显示不兼容原因）。`"2.0.0"` 这种精确写法也**能用**（semver 的 `VersionReq` 会当 `^2.0.0` 处理），
但**推荐写显式区间** —— 对人更清楚，也不必去记「精确版号其实是 caret」这条隐含规则。

### 4.1.1 懒加载：`activationEvents` 怎么选

要不要写 `onStartup`，取决于你的引擎启动有多贵：

| 你的扩展 | 建议 | 效果 |
|----------|------|------|
| 纯 UI / 纯皮肤，没有引擎 | 随便（引擎本来就不会拉） | — |
| 有引擎，但用户不常打开 | **别写 `onStartup`**（如 `["onHotkey","onTray","onInvoke"]`） | 应用启动时**不拉引擎**，首次热键/托盘打开或首次调用方法时才拉起 —— 启动更快、内存更省 |
| 有引擎，且需要开机就在后台干活（索引、同步、托盘常驻） | 写 `["onStartup"]` | 启用即拉起 |
| 不写这个字段 | 等同 `["onStartup"]` | 旧包行为 |

一条「懒加载不会让你漏掉调用」的保证（写引擎时不用自己兜）：

- **方法路径**：`ext_invoke` 发现引擎还没起来，会**先拉起再转发**。
  你的 UI 第一次调任何方法，引擎都会被拉起来，不需要自己调一个"启动"方法。

所以懒加载唯一的代价只是「第一次调用要多等一次引擎启动」（Python 引擎通常 1 秒内）。

> 早期版本在「打开扩展窗口」时也会顺带预热引擎，现已**移除**，原因是它有两个毛病：
> 预热要等 `READY <port>` 握手（最长 20 秒），按热键到窗口出现会卡住；
> 而且它与前端挂载后的首次调用并发，两边都会看到"还没有端口"而各拉起一个引擎 ——
> 后者覆盖前者的句柄，前一个子进程不会被 kill，等于泄漏进程。
> 现在只有 `ext_invoke` 这一条拉起路径，不存在并发。

### 4.2 `engines`：扩展引擎

```jsonc
"engines": {
  "cmd": "engine/serve.py",          // 相对扩展根目录；Windows 下非 .exe 结尾会自动补 .exe
  "args": ["--service", "--port", "0"],
  "supportEnv": "MY_EXT_DATA_DIR",   // 可选：把扩展 data/ 目录写进这个环境变量
  "readyLine": "READY <port>"        // 声明用；真正的握手见第七章
}
```

| 字段 | 类型 | 必需 | 说明 |
|------|------|------|------|
| `cmd` | string | ✅ | 引擎入口文件路径，**相对扩展根目录**。以 `.py` 结尾 → 用系统 Python 解释器（依次探测 `python` / `python3` / `py`）拉起；否则直接执行，Windows 上自动补 `.exe` |
| `args` | string[] | ⬜ | 传给引擎的命令行参数 |
| `supportEnv` | string | ⬜ | 环境变量名。宿主会把 `<扩展目录>/data` **创建好**并用这个名字注入，引擎不用自己猜路径 |
| `readyLine` | string | ⬜ | 声明性字段（可读性 / 未来使用）。当前握手固定是「stdout 出现 `READY <port>`」 |

引擎的运行环境（这些是硬事实，写引擎时要按它来）：

- 工作目录 = 扩展根目录；
- **stdout 被宿主接管**（只读第一行 `READY`，之后就没人读了），日志请走 **stderr** 或自己的文件；
- stderr 重定向到空设备（Windows 下不弹控制台窗口，也不留日志）；
- 超时：`READY` 20 秒；单次方法调用 30 秒。

### 4.3 `web`：扩展前端

| 字段 | 类型 | 必需 | 默认 | 说明 |
|------|------|------|------|------|
| `dist` | string | ⬜ | `"web/dist"` | 预构建静态产物目录，**相对扩展根目录**，里面必须有 `index.html`。允许形如 `"web/dist"` 的多级路径 |
| `defaultRoute` | string | ⬜ | `""` | 默认路由。宿主打开扩展窗口时会带上它，同一份产物可以用 `?route=` 切页面 |

宿主加载扩展 UI 的实际地址（了解即可，你不用自己拼）：

```
http://ext.localhost/<扩展 web/dist/index.html 的绝对路径（URL 编码）>?ext=<扩展 id>&route=<路由>
```

对应前端 `convertFileSrc(htmlPath, "ext")`。这是一条**独立 origin**（见 6.5）。

### 4.4 `contributes`：贡献点

贡献点是**数据不是代码** —— 宿主在跑你的任何代码之前就能解析它、渲染它。

#### 4.4.0 先把「扩展 UI 放哪」选对（最重要的一步）

宿主提供**三条路**，先想清楚你要哪条，再去看字段细节：

| 方式 | 声明 | 用户怎么看到 | 适合 |
|------|------|--------------|------|
| **嵌进主界面**（推荐默认） | `contributes.nav[]` 或 `contributes.ui[]` | 导航栏多一项 / 页面里多一块，**点一下就切过去** | 大多数扩展。用户不需要记热键 |
| 独立窗口 | `contributes.windows[]` + `hotkeys` | 按热键或走托盘**弹一个框** | 悬浮工具、需要在别的应用之上、需要独立尺寸的 |
| 纯后台 | 只写 `engines` | 没有界面，靠托盘/热键触发 | 索引、同步这类 |

> **为什么默认推荐「嵌进主界面」**：独立窗口的问题不是技术性的，是**发现性**的 ——
> 用户装完扩展，如果不记得你声明的热键、也没去翻托盘菜单，他就永远不知道这东西存在。
> 而导航栏多一项是**自解释**的：看得见、点得着。
> 何况「扩展管理」页里也列得出你注册了什么（见 §4.4.6）。

三条路可以同时用：嵌一块常用面板 + 留一个热键弹独立窗口，是很常见的组合。

#### 4.4.1 `nav` / `ui`：往主界面注入 UI

`contributes.nav[]` 是「在主界面导航栏加一项」的简写：``"nav"``。点它会在主窗口内容区
打开你的扩展页面（**不弹窗**）。

```jsonc
"contributes": {
  "nav": [
    { "id": "themes", "title": "皮肤", "icon": "palette", "route": "themes" }
  ]
}
```

`contributes.ui[]` 是通用形式，除了导航项还能往**页面里**塞一块：

```jsonc
"contributes": {
  "ui": [
    // 内容区顶部的一块（所有页面都显示）
    { "surface": "main", "id": "banner", "title": "状态条", "route": "panel", "height": 120 },

    // 只挂到「视频」页上，排在内容下方
    { "surface": "main", "id": "hint", "title": "视频页提示", "route": "hint",
      "position": "bottom", "showOnRoutes": ["/videos"], "height": 96 }
  ]
}
```

| 字段 | 类型 | 必需 | 默认 | 说明 |
|------|------|------|------|------|
| `surface` | `"nav"` \| `"main"` | ✅ | — | 导航栏一项 / 内容区一块 |
| `id` | string | ✅ | — | 扩展内唯一，用于区分同一扩展的多个注入点 |
| `title` | string | ✅ | — | 导航项文案 / 内容块的标题 |
| `icon` | string | ⬜ | `extension` | Material Symbols 图标名（导航项用） |
| `route` | string | ⬜ | `web.defaultRoute` | 加载你前端的哪条路由 |
| `position` | `"top"` \| `"bottom"` | ⬜ | `"top"` | `main` 时排在内容上方还是下方 |
| `showOnRoutes` | string[] | ⬜ | 全部页面 | `main` 时只挂到这些宿主路由上（前缀匹配） |
| `height` | number | **`main` 必需** | — | 内容高度 px |

> ⚠️ **`main` 必须写 `height`**。嵌入用的是 iframe，**iframe 无法按内容自适应高度** ——
> 不声明就是 0 高，等于看不见。宿主在安装时会直接拒绝缺 `height` 的 `main` 注入点，
> 就是为了不让你花时间 debug 一个「装了但什么都没有」的扩展。

> ⚠️ `icon` 只能填**主程序字体子集里已有的**图标名。主程序用的是 Material Symbols 的
> **子集字体**（约 268 个），不在子集里的名字会显示成空白。稳妥做法：
> 挑主界面已经在用的常见图标（`palette` / `storage` / `folder` / `extension` / `search` 等），
> 或者干脆不填 —— 默认的 `extension` 一定在。

> ⚠️ 扩展 UI 是**独立文档**（`ext:` 协议），主程序的 CSS 变量与字体**不会**传进去。
> 你的界面要自带样式；字体想用 Material Symbols 得自己引。

#### 4.4.2 `windows`：扩展窗口

```jsonc
"windows": [
  { "route": "home", "title": "我的面板", "width": 760, "height": 520,
    "alwaysOnTop": true, "decorations": false }
]
```

| 字段 | 类型 | 必需 | 默认 | 说明 |
|------|------|------|------|------|
| `route` | string | ✅ | — | 路由名，与 `?route=` 对应 |
| `title` | string | ✅ | — | 窗口标题，最终显示为 `<产品名> · <title>` |
| `width` / `height` | number | ⬜ | 760 / 520 | 逻辑像素 |
| `alwaysOnTop` | bool | ⬜ | `false` | 置顶 |
| `decorations` | bool | ⬜ | `false` | **系统标题栏**。默认无边框，扩展 UI 自己画标题栏 |

> ⚠️ **所有扩展共用一个窗口**（Tauri label `extension`）。`width` / `height` / `alwaysOnTop` /
> `title` 每次导航都会重新套用；`decorations` **只在窗口第一次创建时生效**，
> 之后切换扩展不会重建窗口，所以它其实取决于「第一个打开扩展窗口的扩展」。
> 别把 `decorations: true` 当成可靠的样式选择，默认无边框 + 自绘标题栏是唯一稳的姿势。
>
> 无边框窗口靠 CSS 拖拽：标题栏元素用 `-webkit-app-region: drag`，
> 里面的按钮等可点区域必须显式写 `-webkit-app-region: no-drag`，否则点不动。

#### 4.4.3 `hotkeys`：全局热键

```jsonc
"hotkeys": [
  { "accelerator": "Ctrl+Alt+Space", "route": "search", "action": "toggle" }
]
```

| 字段 | 类型 | 必需 | 默认 | 说明 |
|------|------|------|------|------|
| `accelerator` | string | ✅ | — | 修饰键 + 主键，如 `Ctrl+Alt+Space`、`CmdOrCtrl+Shift+K`。解析失败只在日志里报错，不阻断启动 |
| `route` | string | ⬜ | `""` | 触发时导航到哪个路由 |
| `action` | string | ⬜ | `"toggle"` | 当前仅 `toggle`：窗口开着就关、关着就开 |

热键由宿主持有并注册，扩展拿不到全局热键权限 —— 这是「宿主代执行」的一部分。

#### 4.4.4 `tray`：托盘菜单项

```jsonc
"tray": [
  { "id": "search",  "title": "内容搜索", "action": "open:search" },
  { "id": "reindex", "title": "重建索引", "action": "invoke:index" }
]
```

| 字段 | 类型 | 必需 | 说明 |
|------|------|------|------|
| `id` | string | ✅ | 扩展内唯一。宿主拼成菜单 id `ext:<扩展 id>:<id>` |
| `title` | string | ✅ | 菜单文字 |
| `action` | string | ⬜ | `open:<route>` 打开扩展窗口；`invoke:<method>` 调用引擎同名方法（payload 为 `null`） |

#### 4.4.5 `themes`：扩展自带皮肤

```jsonc
"themes": [
  { "id": "aurora", "name": "极光", "path": "themes/aurora/skin.json" }
]
```

| 字段 | 类型 | 必需 | 说明 |
|------|------|------|------|
| `id` | string | ✅ | 主题 id，在**扩展命名空间内**唯一。宿主以 `(扩展 id, 主题 id)` 二元组寻址 |
| `name` | string | ✅ | 显示名 |
| `path` | string | ✅ | **扩展目录内** skin.json 的相对路径 |

皮肤格式（v1 纯 JSON / v2 ZIP 资产包）完全沿用[皮肤开发指南](./archive/皮肤开发指南.md)。
完整案例见 `example/extensions/skin-manager/` 与第八章。

#### 4.4.6 `settings`：设置面板 schema

```jsonc
"settings": {
  "schema": [
    { "key": "roots",     "type": "paths", "label": "索引目录", "default": [] },
    { "key": "protect",   "type": "bool",  "label": "敏感目录保护", "default": true },
    { "key": "maxThreads","type": "number","label": "并发数", "default": 4 },
    { "key": "engine",    "type": "enum",  "label": "检索后端",
      "default": "builtin", "options": ["builtin", "remote"] }
  ]
}
```

| 字段 | 类型 | 必需 | 说明 |
|------|------|------|------|
| `key` | string | ✅ | 设置键，读写走 `settings:get` / `settings:set` |
| `type` | string | ✅ | `"bool"` \| `"text"` \| `"number"` \| `"paths"` \| `"enum"` |
| `label` | string | ✅ | 显示名 |
| `default` | any | ⬜ | 默认值。与 `type` 对应（`paths` → string[]，`enum` → string） |
| `options` | string[] | `enum` 时必需 | 可选项 |

> `schema` 当前是**宿主解析、声明即生效**的开放 JSON 数组：宿主按它渲染设置 UI，
> 值由宿主按扩展 id 分开存储，你的 UI 通过 `settings:get` / `settings:set` 读写。

### 4.5 `permissions` / `activationEvents`

见第五章与 4.1 的说明，这里只强调写法：

```jsonc
"permissions": ["ext:invoke", "opener:open-path"],
"activationEvents": ["onHotkey", "onTray", "onInvoke"]
```

## 五、权限模型

### 5.1 两个权限

| 权限 | 管什么 | 什么时候需要 |
|------|--------|--------------|
| `ext:invoke` | 调用扩展引擎的**任意**方法（也就是经宿主转发的每一次 `invoke`） | 只要你调引擎方法就需要 |
| `opener:open-path` | 宿主代执行 `open` / `reveal`（打开文件、在文件管理器里定位、视频跳秒） | 用到 `open` / `reveal` 才需要 |

### 5.2 判定规则（务必理解这两条）

1. **`permissions` 字段整个省略** → 兼容模式，**全部放行**。
   这是为了不搞坏权限模型之前发布的旧包（如参考扩展 miaohui），扩展列表里会标黄提示
   「未声明权限」。**新扩展不要依赖它。**
2. **写了 `permissions` 数组** → 逐项严格校验，没有的就是没有，
   调用直接被拒：`扩展 <id> 未声明 ext:invoke 权限，拒绝 <method>`。

### 5.3 高权限动作真的不转发给引擎

`open` / `reveal` 这两个方法名被宿主**截胡**：宿主检查 `opener:open-path` 后自己执行，
**不会** POST 到你的引擎。所以：

- 你的引擎不需要（也无法）实现 `open` / `reveal` 方法；
- 但**从扩展 UI 发 `open` 一样要声明 `opener:open-path`** —— 权限判在宿主收到请求的那一刻；
- `open` 的 payload 支持 `{ path, ts?, reveal? }`：
  `ts`（秒）用于视频文件 —— 宿主会优先找 mpv / PotPlayer 做精确跳秒，找不到才交给系统默认程序。

### 5.4 最小权限建议

**未知权限名会被忽略，不报错** —— 但也不会生效。请只使用上表列出的两个名字，
不要发明 `fs:read`、`network` 之类看起来合理的权限名然后以为写了就有用。

按需声明，别抄别人的权限清单：

```jsonc
// 只有引擎、不碰文件：一个就够
"permissions": ["ext:invoke"]

// 纯 UI + 纯皮肤扩展（不调引擎）：甚至可以写空数组，表达「我什么都不要」
"permissions": []
```

## 六、扩展 UI ↔ 宿主：postMessage 桥

### 6.1 为什么是 postMessage

扩展 UI 跑在一个 **iframe** 里，它没有 `@tauri-apps/api`、没有 `invoke`、没有文件系统。
它能做的只有一件事：**跟宿主页说话，由宿主页代为执行**。

```
┌──────────────────────────────────────────────────────────────┐
│ 扩展窗口（Tauri label: extension）                            │
│                                                              │
│  ExtensionHost.vue（宿主页，有 IPC 能力）                      │
│   └── <iframe src="http://ext.localhost/...?ext=&route=">      │
│        └── 你的扩展 UI（无 IPC 能力）                          │
│              │  postMessage({ type:"invoke", ... })           │
│              ▼                                                │
│        ExtensionHost 转发 → ext_invoke → 宿主 / 引擎            │
│              │  postMessage({ type:"invoke-result", ... })    │
│              ▼                                                │
│        你的扩展 UI                                            │
└──────────────────────────────────────────────────────────────┘
```

### 6.2 消息格式（就这两种）

**扩展 → 宿主**：

```jsonc
{
  "source": "ext:<扩展 id>",     // 必须精确等于 "ext:" + 你的 manifest.id
  "type": "invoke",
  "reqId": "唯一请求号",          // 你自己生成；宿主原样回传
  "method": "方法名",
  "payload": { }                 // 任意 JSON；没有就传 {}
}
```

**宿主 → 扩展**：

```jsonc
{
  "source": "lumiluna-host",     // 固定标识，与你的 id 无关；是历史名字，不会改
  "type": "invoke-result",
  "reqId": "原样回传",
  "ok": true,                    // 失败时 false
  "data": { },                   // ok=true 时存在
  "error": "错误文本"             // ok=false 时存在
}
```

宿主**丢弃**任何 `source` 对不上、`type` 不是 `invoke`、或没有 `reqId` 的消息 ——
静默丢弃，不报错，不回复。调试时先检查这三个字段。

### 6.3 方法名分两类

**A. 宿主保留方法** —— 不转发给引擎，由宿主自己处理：

| 方法 | payload | 返回 | 权限 |
|------|---------|------|------|
| `settings:get` | `{}` | `{ values: Record<string, unknown> }` | `ext:invoke` |
| `settings:set` | `{ values: Record<string, unknown> }` | `{ ok: true }` | `ext:invoke` |
| `open` | `{ path, ts?, reveal? }` | `{ ok: true }` | `opener:open-path` |
| `reveal` | `{ path }` | `{ ok: true }` | `opener:open-path` |

**B. 转发方法** —— 剩下所有名字都 `POST http://127.0.0.1:<引擎端口>/<方法名>`，
payload 原样作为请求体，引擎的 JSON 响应原样作为 `data` 返回。

方法名由你定：`search` / `index` / `status` / `openResult` …… 只要引擎里实现了同名路由。

> 命名约定：宿主保留方法用 `域:动作` 形式（`settings:get`）。
> **皮肤相关的宿主方法** `themes:list` / `themes:apply` / `themes:clear` 见第八章。

### 6.4 别混淆两层：桥方法 vs Tauri 命令

新手最容易糊涂的地方，一次说清：

| | 桥方法（postMessage） | Tauri 命令（`invoke`） |
|---|---|---|
| 谁在调 | **你的扩展 UI**（iframe 里） | 宿主前端（主窗口 / 扩展窗口的宿主页） |
| 长什么样 | `settings:get`、`themes:apply`（带冒号） | `ext_list`、`ext_get`、`ext_theme_load`（下划线） |
| 从哪发 | `window.parent.postMessage(...)` | `@tauri-apps/api` 的 `invoke` |
| 你能用吗 | ✅ **这是你唯一的通道** | ❌ iframe 里没有 Tauri IPC，调不到 |
| 举例 | `invoke("themes:apply", { extId, themeId })` | 宿主收到后内部走 `ext_theme_load` 把数据读出来 |

一句话：**桥方法是路，Tauri 命令是宿主自己家里的电线。** 你只走路。

### 6.5 origin：为什么扩展不能直接 fetch 本机文件

扩展 UI 由自定义协议 `ext:` 提供，在 Windows 上是 `http://ext.localhost/<绝对路径>`。

这条协议**只服务扩展根目录以内的文件**（含 `..` 的路径、越出扩展目录的路径一律 403）。
它和老的 `asset://`（`http://asset.localhost`）**不同源**，因此扩展 UI 想
`fetch()` 一个 `asset:` 地址读本机任意文件会被跨域挡下。

对你的影响：

- 扩展自己的静态资源**相对路径引用即可**（`./style.css`、`./main.js`），同源；
- 想读扩展目录外的文件 → 没有这条路，请让引擎读，或者用 `open` 让宿主代开；
- iframe 是**跨 origin** 的，所以桥消息必须用 `window.parent.postMessage(msg, "*")`，
  不能用具体 origin。

### 6.6 可直接照抄的 `ExtBridge`

把下面这段放进你的产物（原生 JS，无依赖，任何构建工具或手写 HTML 都能用）：

```js
/** ===== SilverMoon 扩展桥（扩展 API v2） ===== */
const EXT_ID = "hello-world";        // ← 必须与 manifest.id 完全一致
const HOST_SOURCE = "lumiluna-host"; // ← 宿主固定标识，永远不要改
const EXT_SOURCE = `ext:${EXT_ID}`;
const INVOKE_TIMEOUT_MS = 30000;     // 宿主侧超时也是 30s

let seq = 0;
const pending = new Map();

window.addEventListener("message", (ev) => {
  const m = ev.data;
  // 只认宿主的回复；其余消息一律忽略（同页面的其他 postMessage 也会打这里）
  if (!m || m.source !== HOST_SOURCE || m.type !== "invoke-result") return;
  const p = pending.get(m.reqId);
  if (!p) return;
  pending.delete(m.reqId);
  m.ok ? p.resolve(m.data) : p.reject(new Error(m.error || "调用失败"));
});

/** 调用宿主 / 引擎方法 */
function invoke(method, payload = {}) {
  return new Promise((resolve, reject) => {
    const reqId = `${EXT_ID}-${++seq}`;
    pending.set(reqId, { resolve, reject });
    window.parent.postMessage(
      { source: EXT_SOURCE, type: "invoke", reqId, method, payload },
      "*", // 宿主页与扩展不同源，只能是 "*"
    );
    setTimeout(() => {
      if (pending.delete(reqId)) reject(new Error(`调用超时：${method}`));
    }, INVOKE_TIMEOUT_MS);
  });
}

/** 快捷方式：宿主保留的四个方法 */
const settings = {
  get: () => invoke("settings:get").then((r) => r.values ?? {}),
  set: (values) => invoke("settings:set", { values }),
};
const openPath = (path, ts, reveal) => invoke("open", { path, ts, reveal });
```

## 七、引擎协议

扩展引擎是一个**你自己写的本地 HTTP 服务**。宿主只跟它说两件事：启动握手、方法调用。

### 7.1 启动握手

引擎启动后，往 **stdout** 打一行：

```
READY 51234
```

- 宿主**逐行扫描** stdout，按 manifest 里 `engines.readyLine` 声明的模式匹配
  （缺省 `READY <port>`），匹配上就取端口。
  **不是只读第一行** —— 引擎在就绪前先打几行日志是允许的；
- 该模式按空白切段、逐段比对，`<port>` 那一段解析成端口。
  所以 `"listening on <port>"` 这类自定义就绪行同样可用，改 manifest 即可，不必改宿主；
- 20 秒内没匹配到 → 引擎启动失败（日志 `[ext] 启动引擎 <id> 失败`），扩展在 UI 上仍显示「已启用」，
  但调用时会尝试重新拉起；
- 端口建议用 `0` 让操作系统分配，再把真实端口打出来 —— 不要写死端口，会撞车。

Python 侧的最小实现：

```python
import json, os, sys, threading
from http.server import BaseHTTPRequestHandler, ThreadingHTTPServer

class Handler(BaseHTTPRequestHandler):
    def do_POST(self):
        method = self.path.strip("/")            # /search → "search"
        n = int(self.headers.get("Content-Length") or 0)
        payload = json.loads(self.rfile.read(n) or b"{}")
        data = dispatch(method, payload)          # 你自己实现
        body = json.dumps(data).encode("utf-8")
        self.send_response(200)
        self.send_header("Content-Type", "application/json")
        self.send_header("Content-Length", str(len(body)))
        self.end_headers()
        self.wfile.write(body)

    def log_message(self, *a):                   # 日志走 stderr，别污染 stdout
        print(*a, file=sys.stderr)

server = ThreadingHTTPServer(("127.0.0.1", 0), Handler)
print(f"READY {server.server_address[1]}", flush=True)   # ← 必须 flush
server.serve_forever()
```

### 7.2 方法调用

```
POST http://127.0.0.1:<port>/<method>
Content-Type: application/json

<payload 原样>
```

| 事项 | 约定 |
|------|------|
| 路径 | `/<方法名>`，与前端 `invoke("方法名")` 一致 |
| 请求体 | 前端 `payload` 的 JSON；托盘 `invoke:` 触发时为 `null` |
| 响应 | 必须是 JSON（宿主做 `resp.json()`），失败会报「扩展引擎返回非 JSON」 |
| 超时 | 30 秒 |
| 错误 | 用 HTTP 非 2xx 或 `{ "error": "..." }` 表达都行 —— 但**返回体必须是 JSON** |

### 7.3 铁律

1. **stdout 只用来打 `READY` 那一行**，之后别再用（宿主只读到第一行就停了，
   后续输出没人消费，写多了可能把管道写满）。日志一律 stderr 或文件。
2. **只监听 `127.0.0.1`**，不要 `0.0.0.0` —— 这是本地服务，不是网络服务。
3. **不要假设 `data/` 之外能写**。需要持久化就写 `os.environ[supportEnv]` 指向的目录。
4. 引擎是**全权限子进程**（跟主程序同用户），所以恶意扩展 ≈ 恶意软件。
   作为作者，这是你的责任；作为用户，装扩展 = 装软件，请只装信任来源的包。

## 八、皮肤即扩展（新模型）

> 这一章描述的是**新的分发模型**：设置页的皮肤入口将被移除，
> **皮肤不再由设置页管理，而是扩展的职责** —— 用户「装皮肤」= 「装扩展」。
> 皮肤文件本身（skin.json）的格式没有任何变化，仍然以[皮肤开发指南](./archive/皮肤开发指南.md)为准。

### 8.1 模型

| | 旧模型 | 新模型 |
|---|---|---|
| 皮肤从哪来 | 用户拖一个 `.json` / `.zip` 进窗口 | 皮肤随**扩展包**分发（`contributes.themes`） |
| 谁管理皮肤列表 | 设置 → 外观 → 皮肤（内建 UI） | **扩展自己的 UI** |
| 谁负责应用皮肤 | 设置页 | 扩展 UI 调宿主桥方法 |
| 用户在设置页看到什么 | 皮肤列表 / 导入按钮 | 不再有皮肤入口（用户去扩展里管理） |

好处很直接：皮肤作者可以附带动辄几 MB 的背景图/字体、可以写任意管理界面（预览、分类、一键换肤）、
可以和扩展的其它能力（比如「按当前播放歌曲自动换肤」）放在一个包里。

### 8.2 扩展侧要做什么

**① manifest 声明自带皮肤**

```jsonc
"contributes": {
  "themes": [
    { "id": "aurora", "name": "极光", "path": "themes/aurora/skin.json" },
    { "id": "sakura", "name": "樱",   "path": "themes/sakura/skin.json" }
  ]
}
```

`themes[].id` 是**扩展命名空间内**的 id；宿主以 `(扩展 id, 主题 id)` 二元组寻址，
与旧 `skins/` 库里的皮肤 id 不共享命名空间。

**② 目录里放 skin.json**

```
skin-manager/
├── manifest.json
├── themes/
│   ├── aurora/skin.json            ← 纯令牌皮肤（v1）
│   └── sakura/
│       ├── skin.json               ← 带背景图的皮肤（v2）
│       └── assets/bg.png
└── web/dist/index.html
```

skin.json 就在扩展目录里，用**相对路径**引用同目录的 assets（`assets/bg.png`），
和 v2 皮肤包里的写法一样 —— 基准永远是 skin.json 自己所在的目录（见 ④）。

**③ UI 里调宿主的皮肤桥方法**

扩展 UI 只用桥方法（`域:动作`），宿主内部再去走 `ext_themes` / `ext_theme_load` 这两条 Tauri 命令 ——
这个两层关系见 6.4。

| 桥方法 | payload | 返回 | 说明 |
|--------|---------|------|------|
| `themes:list` | `{ extId? }` | `{ themes: [{ extId, id, name, path, dir, absDir }] }` | 列出**所有已启用扩展**声明的主题；每项都带 `extId`。**请按 `extId` 过滤出你自己的那几套** —— 它是全量的。payload 传 `{ extId }` 则只返回该扩展的 |
| `themes:apply` | `{ extId, themeId }` | `{ ok: true }` | 应用主题 |
| `themes:clear` | `{ extId? }` | `{ ok: true }` | 恢复默认外观（不应用任何扩展主题） |

> ⚠️ 返回的是 **`{ themes: [...] }` 这个对象**，不是裸数组 —— 与 `settings:get` 返回
> `{ values }` 同一风格（宿主保留方法统一用「带字段名的对象」，好在不破坏兼容的前提下加字段）。
> 本仓库曾因这个形状在**指南 / SDK / 示例**三处写得不一样，导致皮肤管理器一直显示「共返回 0 套」。
> 以本节与 SDK 的 `theme.list()` 为准。
>
> 为什么 `themes:list` 是全量的：**这是有意设计**。管理器类扩展（比如本仓库的
> `skin-manager` 示例，或者你写的「皮肤市场」）需要能列出机器上所有可用的扩展皮肤，
> 而不是只看得到自己包里那几套。所以它返回全部，过滤是你的活儿。

宿主内部对应的 Tauri 命令（**你不直接调，但知道它存在有助于排查**）：

| 命令 | 返回 |
|------|------|
| `ext_themes()` | `[{ extId, id, name, path }]` |
| `ext_theme_load(extId, themeId)` | `{ json: string \| null, dir: string, absDir: string, files: string[] }` |

**④ 路径基准：`dir` 从扩展根算起，`files` 从主题目录算起**

`ext_theme_load` 的返回（宿主内部命令，扩展 UI 调不到，但你排查问题时会用到）：

```jsonc
// ext_theme_load("skin-manager", "sakura") 的返回
{
  "json":   "{ \"formatVersion\": 2, ... }",  // skin.json 原文
  "dir":    "themes/sakura",                 // ← 相对【扩展根目录】
  "absDir": "C:\\...\\extensions\\skin-manager\\themes\\sakura",  // 绝对路径，引擎/宿主内部基准
  "files":  [                                // ← 相对【主题目录本身】，与 skin_load 同口径
    "skin.json",
    "assets/bg.png"
  ]
}
```

三样东西，三个基准，看这张表就够：

| 字段 | 基准 | 例 |
|------|------|-----|
| `dir` | **扩展根目录** | `themes/sakura` |
| `absDir` | **绝对路径**（宿主/引擎内部用） | `C:\...\extensions\skin-manager\themes\sakura` |
| `files` | **主题目录本身**（= `skin.json` 所在目录） | `skin.json`、`assets/bg.png` |
| skin.json 内部的 `image` / `icons.svg.dir` / `icons.font.file` | **主题目录本身**（与 `files` 同基准） | `assets/bg.png` |

**关键点：`files` 与 skin.json 内部的引用是同一个基准（主题目录），所以 `files` 可以直接喂给校验器。**
宿主就是这么做的：

```ts
const { json, dir, files } = await invoke("ext_theme_load", { extId, themeId });
const v = validateSkin(json, { files });          // ✅ files 已是主题目录内相对路径，直接可用
// base = <appData>/extensions/<extId>/<dir>，用来把 skin.json 里的相对引用拼成绝对路径
```

绝对路径的拼法：`<appData>/extensions/<extId>/` + `dir` + `/` + 引用 ——
例如 `.../extensions/skin-manager/themes/sakura/assets/bg.png`。图片经 `ext:` 协议取（独立 origin）。

其余照旧：

- 宿主用仓库里既有的 `src/utils/skinSchema.ts` 校验器解析 `json`（v1 / v2 都支持），
  再合并进 `src/stores/skins.ts`；
- 校验失败会拒绝应用并回错误文本，你的 UI 直接展示即可；
- 持久化键是 `ext:<extId>:<themeId>`；内置皮肤 id 受正则限制不可能含 `:`，所以不会撞。

**⑤ 皮肤坏了要有退路**

皮肤可能把界面改坏。你的扩展 UI **必须**提供一个「恢复默认外观」按钮，调 `themes:clear`。
应用本身还保留了 `--safe-mode` 启动参数作为最后逃生舱。

### 8.3 完整案例

`example/extensions/skin-manager/` 是一个能跑的最小皮肤管理器：
调 `themes:list` 列出全部主题（按 `extId` 过滤出自带的）、点一下调 `themes:apply` 换上、
一键 `themes:clear` 恢复默认。
它的 `themes/` 里放了两个可直接用的皮肤：一个 v1 纯令牌皮肤、一个 v2 带背景图的皮肤，
照抄改改就能用。**它不带引擎**，`themes:*` 桥方法由宿主处理，所以 manifest 里没有 `engines`。

### 8.4 从旧皮肤迁移

| 你的旧资产 | 在新模型里 |
|---|---|
| 单个 `.json` 皮肤（v1） | 放进 `themes/<名字>/skin.json` |
| `.zip` 皮肤包（v2，含 assets/） | 解包后原样放进 `themes/<名字>/` |
| 多个皮肤 | 每套一个子目录，各写一条 `contributes.themes` |

skin.json **一个字都不用改** —— 宿主仍然按同一套 `skinSchema.ts` 校验，
相对路径的基准也仍然是你放 skin.json 的那个目录。

## 九、调试

### 9.1 打开开发者工具

扩展窗口是一个独立的 Tauri 窗口，右键 → 「检查元素」，或在开发模式下用 WebView 的开发者工具。
扩展 UI 的报错只会出现在**那一层 iframe** 的控制台里，宿主页控制台看不到，别找错地方。

### 9.2 桥不通的排查顺序

按这个顺序查，99% 的问题在这里：

1. **`source` 对不对**：必须精确等于 `"ext:" + manifest.id`（大小写敏感）。
2. **`type` 是不是 `"invoke"`**、`reqId` 有没有。
3. **是不是发给了 `window.parent`**：`window.postMessage` 发给自己没用。
4. **看宿主给的回包**：`ok:false` 时 `error` 里有原因（权限被拒 / 引擎未就绪 / 引擎返回非 JSON），
   同时扩展窗口标题栏下方会短暂显示一行红色错误文本。
5. **引擎起没起来**：`READY` 那行是否真的打到了 stdout 且 **flush** 了；
   `.py` 引擎要求系统有 `python` / `python3` / `py`。

### 9.3 常见错误对照

| 现象 | 原因 |
|------|------|
| 扩展列表里出现了但点不动 / 引擎不启动 | `minHostVersion` 不满足，UI 上显示「API 不兼容」 |
| 扩展压根不在列表里 | manifest 解析失败（日志 `[ext] 跳过 …`）、`id` 为空、或没放在 `extensions/<id>/` |
| 安装时报「扩展要求更高的扩展 API 版本」 | `minHostVersion` 区间不匹配当前 `EXT_API_VERSION`（`2.0.0`），或写了 `"*"` |
| 调用报「未声明 ext:invoke 权限」 | `permissions` 里漏了 `ext:invoke`（写了数组就严格校验） |
| 调用报「未声明 opener:open-path 权限」 | 用了 `open` / `reveal` 但没声明该权限 |
| 调用报「扩展引擎未就绪」 | 引擎没声明、可执行文件找不到、`READY` 超时 |
| 扩展窗口白屏 | `web.dist` 路径不对 / 目录里没有 `index.html` / 资源用了绝对路径（`ext:` 只服务扩展目录内） |
| 界面点不动 | 无边框窗口里自绘标题栏的 `-webkit-app-region: drag` 覆盖了按钮，记得给可点元素加 `no-drag` |

### 9.4 常用宿主命令

在宿主页控制台（主窗口的开发者工具）里可以自查：

```js
// 已装扩展摘要（enabled / engineReady / compatible / permissions / defaultRoute）
await window.__TAURI__.core.invoke("ext_list");
// 读完整 manifest（排字段问题最有用）
await window.__TAURI__.core.invoke("ext_get", { id: "hello-world" });
```

## 十、打包与分发

### 10.1 打包

扩展就是一个目录。**打 zip 时注意**：`manifest.json` 必须位于**压缩包根目录**，
不能套一层文件夹（`hello-world/manifest.json` ❌，`manifest.json` ✅）。

```bash
# 在扩展目录内部打包（Windows PowerShell）
cd example/extensions/hello-world
Compress-Archive -Path * -DestinationPath ../hello-world.zip -Force
```

Windows 上注意不要打进 `__MACOSX`、`.DS_Store` 之类的东西（宿主会跳过隐藏项，
但没必要带）。

### 10.2 三种安装方式

| 方式 | 用户操作 | 宿主做的事 |
|------|----------|-----------|
| 文件夹 | 设置 → 扩展 → 「从文件夹安装」 | 复制整个目录到 `extensions/<id>/` |
| ZIP | 「安装 zip 包」 | 解压到 `extensions/__staging/` → 校验 → 移入 `extensions/<id>/` |
| URL | `ext_install({ kind:"url", url })` | 下载 zip → 同上 |

三种方式都**在落盘前**校验 manifest 与 `minHostVersion`：装上也跑不起来的包直接当场拒绝。
同 id 重复安装 = 覆盖更新（旧目录先删）。

### 10.3 分发布建议

- 版本号用语义化版本，宿主的 `ext_list` 会显示它；
- 用 GitHub Release 附 zip，让用户填 URL 或手动下载安装是当前最省事的路径；
- 包越大装得越慢：v2 皮肤的背景图/字体请压缩，单包控制在几十 MB 内。

## 十一、契约速查

| 项 | 值 |
|---|---|
| 扩展 API 版本 | `2.0.0`（`EXT_API_VERSION`）；`minHostVersion` 比的是它 |
| manifest 字段风格 | camelCase |
| 安装位置 | `<app_data_dir>/extensions/<id>/` |
| 启用状态 | `<app_data_dir>/extensions_state.json` |
| 引擎握手 | **逐行扫描** stdout，按 `engines.readyLine`（默认 `READY <port>`）匹配，20s 超时 |
| 调用路由 | `POST http://127.0.0.1:<port>/<method>`，30s 超时，响应必须 JSON |
| 扩展 UI 协议 | `ext:` → `http://ext.localhost/<绝对路径>`（只服务扩展目录内） |
| 扩展窗口 label | `extension`（全部扩展共享） |
| 主界面注入 | `contributes.nav[]`（导航一项）/ `contributes.ui[]`（`surface: "nav" \| "main"`）；`main` **必须给 height** |
| 注入点数据 | `ext_ui_surfaces()` → `[{ extId, extName, surface, id, title, icon, route, position, showOnRoutes, height, relIndex }]` |
| 注入点刷新 | 装 / 卸 / 启用 / 禁用后宿主 emit `ext:ui-changed`，主窗口据此重拉（不必重启） |
| 桥：扩展 → 宿主 | `{ source: "ext:<id>", type: "invoke", reqId, method, payload }` |
| 桥：宿主 → 扩展 | `{ source: "lumiluna-host", type: "invoke-result", reqId, ok, data, error }` |
| 宿主保留（桥）方法 | `settings:get` / `settings:set` / `themes:list` / `themes:apply` / `themes:clear` / `open` / `reveal` / `ui:openWindow` |
| `themes:list` 的返回 | `{ themes: [{ extId, id, name, path, dir, absDir }] }`；payload 传 `{ extId }` 可只取某个扩展的 |
| 主题数据（Tauri 命令） | `ext_themes()` / `ext_theme_load(extId, themeId)` → `{ json, dir, absDir, files }`（`files` 是主题目录内相对路径，可直接喂 `validateSkin`） |
| 权限 | `ext:invoke`、`opener:open-path`；省略 `permissions` = 兼容全放行 |
| 激活事件 | `onStartup` / `onHotkey` / `onTray` / `onInvoke`；省略 = `onStartup`；不含 `onStartup` = 真懒加载 |
